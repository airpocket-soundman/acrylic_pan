# オンデバイス学習による現場キャリブレーションのPC検証（2026-09-27）

## 目的

Solist-AIのオンデバイス学習（ODL、OS-ELM）を使い、設置後に各エリアを数回ずつ叩くだけで
配備済み12クラス分類モデルを現場に合わせられるかを、実機実装の前にPCで確認する。
狙いは、[今後のタスク](future-tasks.md)の「同一条件では良いが別セッションで悪い」
（固定し直し・打撃条件への過適合）を、PCで再学習せずデバイス上で補正することである。

## 方法

- データ: 400 × 300 × 5 mmパネルの検証済み11セッション、7,132打点
  （中央点4セッション、四隅7セッション）
- 分割: 1セッションずつ未知セッションとして除外するLOSO
- 工場モデル: 配備中の最大データ版と同じ条件。入力128、隠れ層32、出力12、
  公式Simulator seed-1のα、hard sigmoid、L2 1、βはbfloat16へ丸める
- キャリブレーション候補: 未知セッションの各クラス先頭10打点。四隅セッションでは
  4隅を巡回する順で取る
- キャリブレーション: 候補からクラスごとにk打点（k = 1, 2, 3, 5, 10）を乱数で選び、
  「全12エリアを1打ずつ」を1周として逐次学習する。乱数シード5通りの平均
- 評価: 未知セッションのうち候補以外の全5,812打点
- ODL更新: 忘却係数1のOS-ELM。初期P = w (G_f + λI)⁻¹ とし、
  キャリブレーション1打を工場データw打分の重みで学習する（float64では同じ重みの
  バッチ学習と一致することをテストで確認）
- 比較: 校正なし、ODL（w、λ、演算精度を変える）、ラベル不要の入力平均補正、
  キャリブレーション打点だけでの再学習

bfloat16条件は、隠れ層ベクトル、P、βを毎回bfloat16へ丸めて`ODL_StartTrain`を近似した。
AxlCOREの内部演算順序は非公開のため、ビット一致ではない。

### 演算精度

float32とfloat64の結果は全条件で一致した。w = 30、10打でのbfloat16近似は90.75%
（λ = 10、float32比 −0.14ポイント）、w = 300では86.39%（λ = 1、−3.1ポイント）で、
重みを大きくするほどbfloat16の劣化が大きい。

## 解釈

1. **効果は確認できたが、上げ幅は中程度**。5打×12エリア（60打）で平均+2.3ポイント、
   10打で+3.0ポイント。最も効いたのは固定状態が他と異なっていた`aa9943ae`で、
   86.8%から5打で95.3%へ戻った。現場キャリブレーションは「条件が変わって崩れた場合の
   復旧」に向く。
2. **四隅の誤りの大半はセッション差ではない**。同じセッションのデータを学習に含めた
   最大データ版でも四隅精度は85.28%であり（[最大データ再学習](model-training-max-data-20260828.md)）、
   ODL後の86.7%とほぼ同じ水準である。隣接エリア境界付近の識別は、入力特徴と
   32ノードの読み出し層の容量が上限を決めていると考えられる。キャリブレーションでは
   解決しない。
3. **工場モデルを事前知識として残すことが必須**。キャリブレーション打点だけで学習すると
   10打でも87.3%で、校正なしより悪い。
4. **重みはw = 30前後が妥当**。w = 1では変化せず、w ≥ 100では少数打で既存の知識を壊して
   四隅セッションが悪化する。λ（1と10）の差は小さい。
5. **悪化するセッションもある**。`ae4338bd`は10打で−2.2ポイントだった。このため、
   確認打の正解数が下がった場合は更新を保存せず、元のβに戻す。
6. ラベル不要の入力平均補正は全条件で悪化したため採用しない。

## ファームウェア実装

この結果を受けて、12クラス分類モデルに現場キャリブレーションを実装した
（`firmware/AcrylicPanCollector/src/apan_calibration.c`、通信仕様は
[ファームウェアREADME](../firmware/AcrylicPanCollector/README.md#現場キャリブレーションmode-4)）。

- 更新はAxlCOREの`ODL_StartTrain`ではなく、**CPUのfloat32でOS-ELMを計算し、
  更新後のβをbfloat16へ丸めて`ODL_SetWeightBeta`で書き込む**。IchiPingプロジェクトでは
  AxlCOREのbfloat16逐次学習が実機160回更新で発散しており、今回のPC近似より実機が悪い。
- ML63Q2557のワークRAMは16 KBで、既存ファームの空きは約3 KBしかない。float32のP
  （4 KB）とβ（1.5 KB）はRAMに置かず、基板のFRAM（MB85RS2MTA、256 KB）へ置いて
  1行ずつ読み書きする。追加RAMは作業ベクトルの316 Bだけで、ビルド後も約2.9 KBの
  空きがある。
- 初期値: 工場βと、配備モデルの学習7,132件から計算した P0 = 30 (G + I)⁻¹
  （`generated/apan_calibration_prior.h`、`python -m sim.odl_calibration_prior`で生成）。
- ホストテストで、FRAM上のfloat32更新がPCのfloat64計算とβ・Pとも1.5×10⁻⁷以内で
  一致することを確認した。βをbfloat16のまま累積する方式（`float32_bf16beta`）でも
  PC上の精度はfloat32と0.1ポイント以内だったが、実装ではFRAMにfloat32のβを持つ。
- 保存: 確定したβをFRAMの別領域へコピーし、CRC32付きヘッダーを最後に書く。
  起動時に工場βのCRC32とβのCRC32が一致した場合だけ読み込む。工場βへ戻すコマンドもある。
- 手順と安全策: `python -m pc.acrylic_pan_monitor.calibrate --port COM3`で、各エリア1打の
  確認、5周（60打）の学習、再確認を行い、確認打の正解数が下がらなかった場合だけ保存する。

## 制約

- キャリブレーションと評価は同じセッション内の打点で、四隅セッションでは中央点、
  中央点セッションでは四隅を校正に使えない。実運用では中央と四隅を混ぜた校正になる。
- bfloat16条件はAxlCOREの近似であり、実機の丸め挙動とは一致しない。

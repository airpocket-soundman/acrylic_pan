# AxlCOREのODL(`ODL_StartTrain`)は、12エリアの現場キャリブレーションで安定するか

現場キャリブレーションは、AxlCOREのbfloat16によるODLではなく、CPUのfloat32でOS-ELMを計算している
(理由と経緯は[odl-calibration-experiment-20260927.md](odl-calibration-experiment-20260927.md))。
IchiPingプロジェクトでは、AxlCOREの逐次学習が実機の160回の更新で発散した。
このボード・このモデルで、AxlCOREの`ODL_StartTrain`が安定するかを、実機で確かめた。

## 方法

- ファームウェア: `APAN_ODL_EXPERIMENT`(`firmware/AcrylicPanCollector/include/apan_odl_experiment.h`)を1にしたビルドだけが、実験用の操作を持つ。通常のファームウェアでは0で、実験用のコードとデータは入らない。
- 同じ打撃を、AxlCOREの`ODL_StartTrain`と、CPUのfloat32のOS-ELM(現行の現場キャリブレーションと同じ計算)の両方で学習した。
  - 初期値は、どちらも工場のβと、事前分布P0(`apan_calibration_prior.h`)。AxlCOREのPには、P0をbfloat16へ丸めて書き込んだ。
  - 忘却係数は1。AxlCOREの目標値は、正解エリアが1、ほかが0のbfloat16の12次元ベクトル。
- 打撃データ: 2点支持の5セッションから、反復番号が5の倍数でない打撃を、各エリア20打、12エリアを1周ずつの20周(240打)に並べた。実際の打撃ではなく、記録済みの波形から、ファームウェアと同じ前処理で作った128点の入力を、ボードへ埋め込んだ(`sim/odl_engine_experiment.py export`)。
- 更新回数: 960回(240打を4周)。160回の6倍。
- 記録: 48回ごとに、AxlCOREのβ(bfloat16)とCPUのβ(float32)をPCへ読み出し、次を比べた。
  - 2つのβの差(最大・平均)、βの最大値、非有限値の数
  - PC上のfloat64のOS-ELM(同じ打撃の並び)との差
  - 評価用の120打(反復番号が5の倍数、各エリア10打)の正解率(12クラス)
- 実行: `python -m sim.odl_engine_experiment run --port COM3 --updates 960 --checkpoint 48`。結果は `artifacts/odl_engine_experiment/report.json`。

| 更新回数 | AxlCORE vs CPU: βの差の最大 | AxlCORE vs CPU: 平均 | AxlCOREのβの最大値 | CPUのβの最大値 | 正解率(AxlCORE) | 正解率(CPU) |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 0 | 0 | 0.617 | 0.617 | 88.3% | 88.3% |
| 48 | 0.0251 | ― | ― | ― | 84.2% | 85.0% |
| 192 | 0.0314 | 0.0067 | 0.754 | 0.742 | 83.3% | 82.5% |
| 384 | 0.0405 | 0.0075 | 0.801 | 0.772 | 81.7% | 80.0% |
| 576 | 0.0437 | 0.0077 | 0.801 | 0.781 | 79.2% | 80.0% |
| 768 | 0.0428 | 0.0081 | 0.797 | 0.790 | 80.0% | 80.8% |
| 960 | 0.0585 | 0.0092 | 0.805 | 0.813 | 81.7% | 79.2% |

- AxlCOREのβに、非有限値(NaN、無限大)は、全チェックポイントで0個だった。βの最大値は、0.62から0.81までで、増え続けることはなかった。
- AxlCOREとCPUのβの差は、最大で0.025から0.059へ、ゆっくり広がった。平均の差は0.007〜0.009で、βの最大値(約0.8)の1%前後である。
- PC上のfloat64のOS-ELMとの差の最大は、AxlCOREが0.033〜0.059、CPUのfloat32が0.003〜0.004だった。
- 評価用の120打の正解率は、96回以降のチェックポイントの平均で、AxlCOREが81.3%、CPUが81.1%、PC上のfloat64が81.0%だった。3つの間に差は見られなかった。
- 1回の更新に、AxlCOREの`ODL_StartTrain`が使う時間は、平均2.08 msだった。実行全体(CPUのOS-ELM、FRAMの読み書き、βの読み出しを含む)は、960回で405秒、1回あたり約0.42秒だった。

## 読み取れること

- 今回の条件(このモデル、このP0、960回の更新)では、AxlCOREのODLは発散しなかった。IchiPingの結果は、ここでは再現しなかった。
- AxlCOREのβは、float32の計算から少しずつずれるが、ずれは960回で最大0.06にとどまり、正解率はCPUと同じだった。
- 正解率は、工場のβの88.3%から、更新するほど81%前後へ下がった。AxlCORE、CPU、PC上のfloat64のどれでも同じように下がっており、丸めの影響ではない。この打撃は工場のβの学習に使った分布と同じ記録で、同じ240打を4周したため、学習が役に立つ条件ではなかった。この実験は、安定性を調べるもので、キャリブレーションの効果を調べるものではない。

## 限界

- ボード1台、12クラスのモデル1つ、記録済みの波形を埋め込んだ打撃による、1回の実行である。実際の打撃や、マレットを替えた条件では試していない。
- 960回より長い更新、エリアに偏りのある並び、忘却係数が1でない設定は、試していない。
- AxlCOREのPは、P0をbfloat16へ丸めて書き込んだ。AxlCOREのPの読み出しは、していない。
- AxlCOREのODLへ切り替えると、FRAMとCPUのOS-ELM、α(8 KiB)のコピーが、不要になる可能性がある。切り替えは、この実験では行っていない。

## ファームウェアの既定の切り替え

この結果を受けて、現場キャリブレーションの更新を、AxlCOREの`ODL_StartTrain`に切り替えた(`APAN_CALIBRATION_ENGINE` が既定で1)。

- 開始(BEGIN): 工場βをAxlCOREへ書き、Pには P0 をbfloat16へ丸めて書く。
- 1打ごとの学習: `ODL_StartTrain`(目標は正解エリアが1のbfloat16ベクトル)。
- 確定(COMMIT): AxlCOREのβを1行ずつ読み出して、FRAMへfloat32で保存する。起動時は、保存済みβをAxlCOREへ読み込む。
- 破棄(DISCARD)、モード切り替え、自己試験などでAxlCOREを初期化すると、作業中のβは失われる(保存済みβまたは工場βへ戻る)。
- α: エンジン方式では、12クラスのモデルのα(4,096個、約8 KiB)をフラッシュに持たず、AxlCOREへ書き込まない。AxlCOREが、`ODL_Initialize`のseedと範囲(`scaleAlpha`)から、同じαを生成する(60クラスのモデルのヘッダーも、βだけを持つ)。CPU方式のビルドでは、αの配列を持つ。
- 確認(`python -m sim.check_class_model_selftest --port COM3`): 12クラスのモデルの固定入力12件を、実機のAxlCORE(αを書き込まないビルド、工場βの作業用キャリブレーション)に通した。12件とも、正解クラスがPCの参照(ヘッダーのαとβ)と一致し、出力の差の最大は0.023(出力の最大値は0.42〜0.98、bfloat16の丸めの範囲)だった。AxlCOREが生成するαは、保存していたαと同じである。
- 保存と再起動: エンジン方式で確定した保存済みβ(60打)は、その後のファームウェアの書き換え・リセットを経ても、有効だった。確認のあとの破棄(DISCARD)で、保存済みβへ戻った。
- ビルドの大きさ: text 58,620 B、data+bss 13,280 B。CPU方式(text 67,312 B、data+bss 13,408 B)より、textが約8.7 KB小さい。
- CPU方式は、`APAN_CALIBRATION_ENGINE` を0にしたビルドで残してあり、ホストテストはこの方式を検証する。エンジン方式のFRAM保存は、ホストテストで確認した。
- 実験用のビルド(`APAN_ODL_EXPERIMENT` = 1)は、両方式を並べて比べるため、CPU方式を使う。
